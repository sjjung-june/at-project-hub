# HCP 이전 인수인계 노트 — 사내 에이전트용

작성일: 2026-11-24

## 요청과 확인 범위

AT 과제 관리 시스템을 **사내 HCP의 기존 Docker·Jenkins 템플릿에 맞춰 이전**한다. 신규 백엔드는 이 폴더의 FastAPI이며, 기존 `../server/`의 Node.js 구현은 참고용이다. HCP 템플릿 원본·사내 레지스트리·Jenkins 공통 라이브러리·배포 명령은 아직 전달받지 못했다. 아래는 저장소에서 확인한 실행 계약과 이관 작업 목록이다. HCP가 Kubernetes, VM, 특정 Jenkins 플러그인을 사용한다고 가정하지 않는다.

확인 기준 소스 커밋: `9e57091b0a7d4b26edaac8c592b981e953da136e`. 이 노트 이후의 구현은 실제 이관 시점의 최신 소스를 다시 확인한다.

- FastAPI 검증: 업무 규칙·HTTP·인증·실제 PostgreSQL 테스트 25건 통과.
- FastAPI Docker 이미지 빌드 통과.
- 프런트엔드/기존 모델 검증 91건 및 기존 Node PostgreSQL 테스트 통과.
- 검증 기록: [FastAPI CI](https://github.com/sjjung-june/at-project-hub/actions/runs/45403105849), [전체 저장소](https://github.com/sjjung-june/at-project-hub).

HCP 배포 및 사내 SSO 연결이 완료된 상태는 아니다. 이 문서는 실제 HCP 설정값이나 사내 접속 정보를 포함하지 않는다.

## 현재 구성과 완료 범위

| 항목 | 현재 상태 | HCP 이관 작업 |
|---|---|---|
| 프런트엔드 | 기존 HTML/JS 화면 + React/styled-components Step 화면, `dist/` 정적 산출물 | 사내 정적 웹 배포 템플릿에 연결 |
| 화면 저장 | 배포된 시연 화면은 브라우저 localStorage 사용 | 비동기 FastAPI 호출로 저장 흐름 전환 필요 |
| 백엔드 | `backend/` 독립 FastAPI, Python 3.12+ | HCP Python/Docker 템플릿에 연결 |
| DB | PostgreSQL 17 테스트, JSONB 과제 문서 + 승인·감사 테이블 | HCP 제공 DB의 버전·접속·권한·백업 확인 |
| 인증 | OIDC RS256 Bearer JWT 검증 연결부 | 사내 SSO 실제 규격과 역할/조직 매핑 적용 |
| CI | GitHub Actions에서 테스트·이미지 빌드 | 같은 검증을 Jenkins 템플릿 단계로 이전 |
| 배포 | 백엔드 Dockerfile, 로컬 Compose 제공 | 사내 이미지 레지스트리·환경별 배포 설정 적용 |
| AI·메신저 | 규칙 기반 Summary와 연동 준비 구조 | 실제 사내 AI 호출·메신저 발송은 별도 연동 작업 |

**이미지만 배포해서는 화면이 공용 DB를 사용하지 않는다.** 공용 API를 사용하는 `../dist/pilot.html`과 `../src/pilot/` 작업공간을 배포하고 실제 인증을 연결해야 공용 시스템이 된다. 기존 index.html은 브라우저 시연이다. HCP 이전 범위가 백엔드만인지 전체 시스템인지 먼저 확인하고, 백엔드만 이전하면 화면 연결은 미완료 항목으로 명시한다.

## 먼저 확보할 사내 자료

사내 에이전트는 아래 값을 HCP 템플릿·운영 문서에서 직접 확인하여 구현한다. 확인되지 않은 값을 임의로 만들지 않는다.

| 확인 항목 | 필요한 정보 |
|---|---|
| 템플릿 | 기준 저장소/브랜치, 템플릿 버전, Dockerfile·Jenkinsfile, 공통 라이브러리 사용 규칙 |
| 빌드 | Jenkins 실행 에이전트, Docker 빌드 방식, Python/Node 지원 버전, CPU 아키텍처 |
| 의존성 | 승인된 Python/Node 베이스 이미지, 사내 PyPI/npm 미러, 프록시·사내 CA 설정 |
| 이미지 | 레지스트리 경로, 이미지 이름 규칙, 태그·digest 관리, 취약점 검사·서명 정책 |
| 배포 | HCP 애플리케이션 등록 방식, 서비스 포트, 배포/상태 확인/롤백 명령 |
| 환경 | 개발·검증·운영 분리, 리소스·복제 수·프로세스 수, 배포 중 트래픽 처리 방식 |
| DB | 제공 PostgreSQL 버전, DB명/schema, TLS·CA, 런타임/마이그레이션 계정, 연결 한도 |
| SSO | issuer/audience/JWKS 또는 실제 사내 인증 규격, 안정적인 사용자 ID·조직 ID·역할의 출처 |
| 라우팅 | 업무 URL, TLS 종료 지점, `/api` 전달 규칙, 외부 경로 prefix, 프록시 헤더 규칙 |
| 운영 | Secret 주입, 로그·모니터링, health probe 규격, 백업/복구, 장애 대응 담당 |

Jenkins credential ID, HCP 서비스명, 레지스트리 주소, 배포 명령, 실제 Secret은 이 공개 저장소나 노트에 기록하지 않는다. 사내 설정 저장소와 Secret 관리 수단을 사용한다.

## 백엔드 실행 계약

파일: `Dockerfile`, `requirements.lock`, `app/main.py`, `app/config.py`, `app/db.py`.

- 빌드 컨텍스트는 **`backend/`**. 저장소 루트에서 실행할 때는 아래와 같다.

```sh
docker build -f backend/Dockerfile -t <사내-이미지명>:<소스-커밋> backend
```

- 현재 베이스는 `python:3.12-slim`. 사내 승인 이미지와 아키텍처로 교체하고 고정 의존성의 wheel 설치 가능 여부를 확인한다.
- 현재 이미지의 실행 사용자는 `appuser`인 비 root 사용자다. HCP가 지정 UID나 읽기 전용 파일시스템을 요구하면 권한과 임시 디렉터리를 조정한다.
- 작업 디렉터리 `/app`, 앱 엔트리포인트 `app.main:app`, 컨테이너 포트 `8000`.
- 현재 기본 명령은 다음과 같다. 운영에서 `--reload`는 사용하지 않는다.

```sh
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

- 의존성은 런타임 `requirements.lock`, 테스트 포함 `requirements-dev.lock`에 고정되어 있다. Python/베이스 이미지 변경 시 테스트와 이미지 빌드를 다시 실행한다.
- `.env`, `.venv`, 테스트 캐시는 이미지에 넣지 않는다. 현재 `.dockerignore`를 유지한다. 사내 저장소 인증정보나 CA 개인키를 이미지 레이어/빌드 인자에 남기지 않는다.
- `compose.yaml`은 로컬 개발 예시다. 여기에 있는 PostgreSQL 컨테이너·로컬 볼륨·`127.0.0.1` 포트 설정을 HCP 운영 설정으로 그대로 옮기지 않는다.

## 환경 변수와 Secret 매핑

| 변수 | HCP 설정 | 비고 |
|---|---|---|
| `APP_ENV` | `production` | 운영 기본값 |
| `DEV_AUTH` | `false` | `production`과 개발 인증을 동시에 켜면 설정 검증 실패 |
| `DATABASE_URL` | 런타임 DB 계정의 PostgreSQL 접속 URL | Secret. TLS 모드·CA 위치를 사내 DB 규격에 맞게 설정 |
| `OIDC_ISSUER` | 사내 토큰 issuer | 실제 발급 토큰과 정확히 일치 |
| `OIDC_AUDIENCE` | 이 API용 audience | 실제 사내 발급 규격 확인 |
| `OIDC_JWKS_URL` | 신뢰할 수 있는 사내 HTTPS JWKS 주소 | API에서 네트워크 접근 및 CA 신뢰 필요 |
| `CORS_ORIGINS` | JSON 배열 형식의 허용 프런트엔드 origin | 동일 출처 `/api` 프록시라면 보통 `[]`; 실제 라우팅으로 검증 |

DB 접속 URL은 브라우저에 전달하지 않는다. Jenkins의 Secret 마스킹만 믿고 값을 출력하지 말고, 셸 디버그 출력·환경 변수 전체 출력도 피한다. 빌드와 테스트 DB, 운영 DB의 credentials를 분리한다.

현재 `Settings`가 `.env`도 읽으므로 운영 이미지에는 `.env`를 넣지 않고 HCP 런타임 Secret/환경 변수로 주입한다. 사내 CA는 승인된 인증서 배포 방식으로 Python의 DB/HTTPS 통신에 적용하며 인증서 검증을 끄는 방식으로 우회하지 않는다.

## Jenkins 단계 매핑

**아래는 단계 계약이다. 실행 가능한 Jenkinsfile이나 HCP 전용 명령이 아니다.** 사내 템플릿의 공통 라이브러리·에이전트·credential 바인딩·배포 절차를 확인한 뒤 그 틀 안에 구현한다.

| 단계 | 수행할 작업 | 실패 시 처리 |
|---|---|---|
| Checkout | 배포할 커밋 확정, 필요한 소스만 체크아웃 | 중단 |
| 의존성 | 사내 미러에서 backend 고정 의존성 설치 | 중단 |
| 백엔드 검증 | 테스트 전용 PostgreSQL을 붙여 `python -m pytest -q` | DB 테스트 skip이면 통과로 보지 않음 |
| 화면 검증/빌드 | 전체 시스템 이관이면 루트에서 `npm ci`, `npm test`, `npm run build` | 중단 |
| 이미지 빌드 | backend 컨텍스트로 이미지 빌드 | 중단 |
| 사내 검사 | 템플릿에서 요구하는 이미지 검사·서명 등 | 사내 기준에 따라 중단 |
| Push | 커밋 기반 태그와 이미지 digest 기록 후 사내 레지스트리에 업로드 | 중단 |
| 검증 환경 배포 | 검증 DB에 마이그레이션 후 같은 이미지 배포, SSO/API 확인 | 운영 승격 중단 |
| 운영 사전 점검 | 백업/복구 지점, DB 호환성, 변경 절차 확인 | 미충족 시 중단 |
| 운영 마이그레이션 | 같은 릴리스 이미지로 별도 1회 작업 실행 | 실패 시 새 앱 배포 중단 |
| 운영 배포 | 검증한 digest를 HCP 템플릿으로 배포 | 호환 가능한 이전 이미지로 복귀 검토 |
| 스모크 테스트 | 인증·조회·저장·승인·이력·충돌 검사 | 트래픽 전환 중단/복귀 |
| 기록 | 커밋, digest, HCP 배포 이력, SQL 적용 버전, 테스트 결과 | 사내 릴리스 이력에 보존 |

테스트 예시의 작업 디렉터리는 `backend/`다.

```sh
python -m pip install -r requirements-dev.lock
python -m pytest -q
```

Jenkins가 `TEST_DATABASE_URL`을 **폐기 가능한 테스트 전용 DB**로 주입해야 한다. 실제 DB 테스트는 임시 schema를 생성·삭제하므로 해당 테스트 계정에는 schema 생성 권한이 필요하다. 현재 테스트는 DB URL이 없으면 일부 테스트를 skip하므로 Jenkins 단계에서 URL 설정 여부와 DB 테스트 실행 결과를 명시적으로 확인한다. 운영 DB를 테스트에 연결하지 않는다.

참고 구현은 `../.github/workflows/fastapi.yml`과 `../.github/workflows/tests.yml`이다. GitHub Actions의 문법과 임시 DB 서비스 정의를 Jenkins에 그대로 복사하지 않는다.

## DB 마이그레이션과 롤백

마이그레이션 엔트리포인트:

```sh
python -m app.db
```

HCP/Jenkins의 별도 작업에서 **배포할 API와 같은 이미지 digest**로 실행하고, 마이그레이션 계정의 DB 접속 Secret을 주입한다. API 컨테이너 시작 때마다 마이그레이션을 반복 실행하도록 바꾸지 않는다.

현재 구현:

- SQL은 `app/migrations/*.sql`, 적용 이력은 `schema_migrations`에 파일명으로 기록한다.
- 같은 DB의 advisory transaction lock으로 동시 마이그레이션을 직렬화한다.
- 새 DB에 `projects`, `change_requests`, `audit_events` 및 감사 이력 변경 차단 트리거를 생성한다.
- 기존 Node 프레임이 같은 `001_initial.sql`을 이미 적용했다면 건너뛴다. 이름만 같고 실제 테이블이 다른 DB는 스키마를 비교해야 한다.
- 적용 파일의 checksum 검증과 자동 downgrade는 아직 없다. 적용된 SQL 파일을 수정하지 말고 다음 번호의 새 파일로 변경을 추가한다.
- 초기 DB 계정에는 테이블·인덱스·함수·트리거 생성 권한이 필요하다. 런타임 계정은 업무에 필요한 조회/쓰기와 감사 이벤트 INSERT만 부여하도록 별도 grant를 구성한다. 현재 저장소에는 이 계정 분리용 운영 grant 스크립트가 없다.

롤백은 앱과 DB를 분리해서 계획한다. 이전 앱이 변경 후 스키마를 읽을 수 있는지 검증하고 이미지 digest를 보관한다. DB는 SQL 삭제나 무조건적 역변환으로 복구하지 않는다. 우선 호환 가능한 이미지 복귀/전진 수정 여부를 판단하고, 실제 데이터 복원이 필요하면 쓰기 중지·백업/PITR·쓰기 손실 범위·재검증을 사내 절차에 따라 수행한다. **현재 초기 스키마 외의 운영 롤백은 검증하지 않았다.**

## 네트워크·라우팅·상태 점검

- 권장 배치: 정적 프런트엔드 + `/api`를 FastAPI로 전달하는 동일 출처 라우팅 + 사내 PostgreSQL.
- 앱 라우트 자체에 `/api`가 포함되어 있다. 프록시에서 `/api`를 제거하거나 이중으로 붙이지 않도록 확인한다.
- 프록시는 `Authorization`, `If-Match` 요청 헤더와 `ETag` 응답 헤더를 보존해야 한다. 그래야 인증과 동시 수정 검사가 동작한다.
- HCP의 외부 prefix가 있다면 FastAPI `root_path`, Swagger/OpenAPI 주소, 정적 경로를 실제 템플릿에 맞춰 검증한다. 현재 별도 prefix 설정은 구현하지 않았다.
- `/api/health`는 DB `SELECT 1`까지 확인하며 인증이 필요 없다. DB가 없거나 접근 불가하면 준비 상태로 볼 수 없다.
- 현재 DB와 무관한 전용 liveness 엔드포인트는 없다. HCP가 liveness/readiness/startup을 나누면 별도 endpoint와 테스트를 추가한다. DB 장애만으로 앱 재시작이 반복되지 않도록 probe 계약을 확인한다.
- Swagger `/docs`, OpenAPI `/openapi.json`은 현재 공개 라우트다. 운영 노출 여부는 HCP 정책에 맞춰 제한하거나 조건부 비활성화한다.
- 월별 실적의 현재 월 판단은 `Asia/Seoul`, 감사 시각은 UTC 기준이다. 사내 베이스 이미지의 시간대 데이터와 화면 표시 시각을 확인한다.
- DB pool은 **프로세스당 최대 10개**다. 전체 최대 연결 수는 대략 `복제 수 × worker 수 × 10 + 마이그레이션/운영 연결`이다. HCP 리소스와 DB 한도에 맞춰 worker/pool을 조정하고 부하 검증한다. pool 크기 환경 설정은 아직 없다.
- JWKS와 DB 연결에 필요한 사내 DNS·아웃바운드·CA·방화벽을 확인한다. ingress만 설정하고 토큰 검증 경로를 빠뜨리지 않는다.
- 로그/요청 추적/지표와 타임아웃은 HCP 공통 템플릿에 연결한다. JWT·DB URL·과제 본문 전체가 로그에 남지 않도록 확인한다.

## SSO·권한 연결 작업

현재는 서명 검증된 토큰의 `sub`, `name`, `at_role`, `at_team`을 사용한다. 검증 항목은 RS256, issuer, audience, 만료와 필수 클레임이다. 실제 HCP/사내 SSO가 다른 토큰·세션 규격이면 `app/auth.py`를 맞춰 구현하고 테스트한다. 프록시의 임의 사용자 헤더를 곧바로 신뢰하는 방식으로 대체하지 않는다.

| 업무 역할 | 내부 role |
|---|---|
| AT 담당 조직 책임자·담당 | `at-head` |
| 팀장 | `team-lead` |
| 시스템 관리자 | `system-admin` |
| 과제 대표자 | `project-representative` |
| 과제 참여자 | `participant` |
| 일반 담당 구성원 | `member` |

조직 역할은 검증된 사내 인증/조직 데이터에서 가져온다. 과제 대표·참여 편집은 서버의 `_ownerId`/`_memberIds`와 안정적인 사용자 ID로 판단하며, PO/PM 이름 입력만으로 편집 권한을 부여하지 않는다. 현재 참여자 ID 지정 API·조직도 연동은 미구현이므로 이관 범위에 포함해 설계한다.

팀장은 자기 팀의 일반 변경을 검토하고, 전체 일정·소속 팀·PO·보관 변경은 담당 검토 대상이다. 자기 승인과 단순 관리자 역할의 자동 승인을 허용하지 않는 기존 규칙을 유지한다. 현재 인증 사용자 전체에게 목록·상세·이력을 보여주므로, 사내 조직별 조회 범위 제한이 필요하면 별도 정책과 테스트를 추가한다.

## 프런트엔드와 데이터 이전에서 빠뜨리면 안 되는 일

- `../src/api-client.js`를 사용하는 신규 `../dist/pilot.html` 작업공간에 등록·실적·첨부·제출/검토·변경 승인·이력을 연결했다. 기존 index.html은 localStorage 시연이다. HCP는 신규 작업공간을 운영 진입점으로 설정한다.
- 목록/상세 조회를 API로 바꾸고 등록·실적·승인·이력의 각 동기 저장 흐름을 비동기 API로 전환한다. 저장 중 상태, 실패 시 입력 보존, 중복 제출, 401 재로그인, 409 최신 데이터 비교/복구를 구현한다.
- 로그인/토큰 발급은 사내 SSO에서 처리한다. `getAccessToken`에 실제 세션의 액세스 토큰을 연결하고, 클라이언트가 역할을 임의 선택하던 시연 UI는 운영 인증 흐름으로 대체한다.
- 브라우저 임시저장을 유지한다면 사용자 ID와 과제 ID별로 구분하고 로그아웃·계정 변경 시 이전 사용자의 초안이 노출되지 않게 한다.
- **화면의 Step 목표/실적은 0~비중, 저장/API는 Step 자체 완료 비율 0~100이다.** 비중 40의 Step에서 화면 20은 API 50, 전체 기여도 20이다. 이 단위를 혼용하거나 가중치를 두 번 곱하지 않는다.
- Step 비중 합계 100, 마지막 목표=해당 비중, 누적 목표/실적 비감소, 기간 외 비활성화, 미래 실적 제한을 유지한다.
- 실적 미입력을 0으로 바꾸지 않는다. 종료된 미완료 Step은 실적/지연 사유/Catch Up Plan 입력을 이어가고, 완료 Step은 이후 월에 이월한다.
- 기존 전체 실적을 Step에 임의 배분하지 않는다. 승인 중 최신 실적과 제거된 Step의 실적/감사 기록을 보존한다.

현재 배포 시연 데이터는 브라우저별 localStorage에 있다. 사이트 파일이나 Docker 이미지를 옮겨도 함께 이동하지 않는다. 실제로 이전할 자료가 있다면 사용자가 명시한 대상만 내보내고, 가상 예시와 실제 데이터를 구분한 뒤 검증·dry-run·중복 방지·사용자 ID 매핑을 갖춘 일회성 가져오기 도구를 만든다. 이 도구는 아직 없다. 기존 등록 API는 새 ID와 소유자를 지정하므로 과거 ID·승인·이력 복원에 단순 POST 반복을 사용하지 않는다.

### 개인 대시보드와 담당 전체 조회 정책 (2026-11-25 확정)

- 로그인 기본 진입점은 개인 대시보드다. 조직 책임자의 화면 명칭은 **담당**이며 OIDC 역할 코드 `at-head`는 기존 계약을 유지한다.
- AT 담당 구성원 전체에게 전체 과제·상세·이력·실적·첨부·요약 읽기를 허용한다. 개인 목록은 편의상 참여 관계를 모아 보는 뷰이며 읽기 권한 제한이 아니다. 수정·보고·승인 권한과 자기 승인 제한은 기존 서버 정책을 유지한다.
- `GET /api/me/projects`는 로그인된 계정 ID의 서버 저장 `_ownerId`, `_memberIds`, 선택적 `_poId`/`_pmId` 관계로 과제를 찾는다. 조회 계정을 클라이언트 쿼리로 받지 않으며 이름 일치로 참여 권한을 만들지 않는다.

- 브라우저 시연 메인의 ‘체험할 사용자’는 이름으로 예시 관계를 보여주는 시연 전용 선택이다. 인증·수정 권한 전환 기능으로 사내에 이식하지 말고 SSO `/api/me`와 위 서버 관계로 교체한다.
- 확인: 일반 구성원은 본인 참여 목록이 비어도 담당 전체를 읽을 수 있으며 수정은 403, 공동 수행자는 계정 ID로 참여 과제를 조회, 동명이인은 참여자로 잘못 포함되지 않아야 한다.

- DB `004_knowledge_documents.sql`을 기존 `python -m app.db`로 적용합니다. 기존 첨부는 첨부 볼륨이 연결된 API 환경에서 `python -m app.knowledge_backfill --limit 200`을 반복 실행합니다. 이미 색인된 파일은 중복 처리하지 않습니다. 파일 누락·해시 불일치는 unavailable 수치로 확인합니다.
- 새 TXT/CSV 첨부는 같은 트랜잭션에서 본문을 색인합니다. UTF-8, 1MB 이하, 최대 120,000자, 조각 최대 4,000자. 다른 파일 형식·초과 파일은 unsupported/too_large로 기록합니다. PDF·Office·OCR는 후속 사내 처리기를 붙여야 합니다.
- 추가 API: GET `/api/projects/{id}/knowledge-context`, POST `/api/knowledge/recommendations`, POST `/api/projects/{id}/knowledge-decisions`. 확인 저장에는 If-Match, contextToken, targetToken을 사용합니다. 서버의 실제 원본에서 확인 근거를 정하고 위조 인용을 거부합니다.
- 근거 변경 판단은 인용 위치·내용·문서 해시 기준입니다. 월별 실적이 추가되었다는 이유만으로 기존 관계를 폐기하지 않습니다. 당시 인용 내용이 바뀐 관계는 확인 수치·확인 관계 노드에서 제외합니다.
- `_knowledgeDecisions`와 경험 카드 sourceEvidence를 프로젝트 JSONB와 기존 audit_events에 보존합니다. 계정·조직 ID가 없는 이름은 과제 범위의 지정 정보로만 취급합니다. `_poId`, `_pmId`, `_memberIds`, `_teamId`는 신뢰된 조직 연동에서 채워야 합니다.
- 사내 AI 연결 시 입력은 사용자에게 허용된 근거 ID·원문·버전으로 제한합니다. 출력은 후보와 인용 ID로 받으며, 존재하지 않는 근거·과제·범위 밖 인용을 거부하고 사람 확인을 거쳐야 합니다. 모델 출력으로 원본 계획·실적·승인 상태를 수정하지 않습니다. 현재는 의미 추론·동의어 검색이 없는 문구 검색입니다.
- 초기 검색은 이력·감사 스냅샷을 제외한 투영 데이터를 사용합니다. 대규모 수년 데이터에서 검색 지연·메모리·문서 처리량을 측정하고 전용 검색 인덱스와 작업 큐를 확장하세요. 전체 조직의 시점별 그래프와 검색 조회 계측은 후속 범위입니다.
