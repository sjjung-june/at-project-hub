# AT 실적 요청 사내 메신저 연동 계약

실적 요청 화면에서 선택한 미입력 과제의 PM에게 월별 누적 진척률 입력을 요청하기 위한 서버 연동 초안입니다. 현재 화면은 요청 준비·취소·실적 입력 확인·연동 요청 파일 준비를 브라우저에 기록합니다. 메시지 발송, SSO 계정 조회, 서버 예약 작업은 구현되지 않았습니다.

## 현재 요청 형식

선택한 연동 대기 요청만 JSON 파일에 포함됩니다. 파일 생성은 발송으로 처리하지 않습니다.

```json
{
  "schemaVersion": "at-report-request-v1",
  "generatedAt": "2026-11-23T01:00:00.000Z",
  "deliveryStatus": "not_sent",
  "requests": [
    {
      "requestId": "요청별 UUID",
      "idempotencyKey": "과제ID:2026-11:담당 PM 이름",
      "recipient": { "name": "예시 PM", "accountId": null },
      "payload": {
        "title": "예시 과제",
        "reportMonth": "2026-11",
        "dueDate": "2026-11-30",
        "deepLink": "https://서비스주소/#report=과제ID&month=2026-11",
        "message": "과제 제목, 대상 월, PM, 입력 기한, 누적 실적 안내와 입력 링크"
      }
    }
  ]
}
```

`accountId: null`은 수신 계정이 확인되지 않았다는 의미입니다. PM 이름만으로 발송하지 않습니다. 공용 과제 DB와 SSO 조직도를 연결한 뒤 과제의 승인된 PM 사번과 메신저 사용자 ID를 서버에서 대응시켜야 합니다. 현재 브라우저 저장 방식에서는 다른 사용자의 브라우저에서 동일한 과제 링크를 조회할 수 없습니다.

## 서버 접수와 재검증

제안 접수 주소는 `POST /api/report-requests`입니다. 브라우저에서 API 키나 메신저 토큰을 전달하지 않고, 로그인 세션으로 호출합니다. 서버는 다음 항목을 재검증한 뒤 요청을 원자적으로 저장하고 작업 큐에 등록합니다.

1. 요청자의 조직 범위와 실적 요청 권한, 과제의 최신 승인 버전.
2. 대상 월이 과제 기간 내이며 현재 월 이후가 아닌지, 누적 목표 계획이 유효한지.
3. 과제가 진행 대상인지. 완료·보류·보관 과제와 해당 월 실적이 이미 입력된 과제는 제외합니다. 실적 0%도 입력 완료입니다.
4. 최신 승인 PM의 SSO 계정과 메신저 수신 ID가 확인되는지. 계정이 없거나 중복 매칭되면 발송을 보류합니다.
5. 입력 기한은 한국 시간 기준 오늘 이후 날짜인지. 화면의 날짜와 서버 검증에 같은 시간대를 사용합니다.
6. 입력 링크는 서버에 설정된 서비스 주소로 생성하고 과제 조회 권한을 다시 확인합니다. 클라이언트가 보낸 외부 링크나 수신 ID를 그대로 신뢰하지 않습니다.

접수 응답은 `requestId`, 서버에서 확정한 `idempotencyKey`, `status`, `acceptedAt`을 반환하도록 합니다. 중복 요청이면 기존 요청 ID와 상태를 반환합니다. 사유가 있는 제외 결과는 과제별로 반환하고, 일부 성공을 전체 성공으로 표시하지 않습니다.

## 중복 방지와 취소

서버의 중복 키는 과제 ID·보고 월·확정 수신 계정 ID로 구성합니다. 이름을 사용한 현재 파일의 키는 서버에서 정규화해야 합니다. 같은 요청 파일을 여러 번 접수하거나 통신 오류 후 재호출하더라도 한 번만 발송되도록 요청 ID 유일성과 활성 중복 키 유일성을 함께 보장합니다.

이미 발송된 동일 월 요청은 재접수로 다시 보내지 않습니다. 취소 후 재준비한 요청은 기존 요청이 실제로 발송되지 않았음을 확인한 경우에만 새 요청으로 접수합니다. 재알림은 별도 회차 정책과 식별자를 사용해야 하며, 전송 실패 재시도와 구분합니다.

제안 취소 주소는 `POST /api/report-requests/{requestId}/cancel`이며 사유를 필수로 받습니다. 취소와 작업 큐의 발송 시작은 같은 서버 상태를 기준으로 제어합니다. 이미 발송된 메시지는 취소된 것처럼 표시하지 않습니다. PM 변경·과제 보류·보관·계획 오류가 생기면 미발송 요청을 취소하고 사유를 남깁니다.

## 발송 작업과 결과

메신저 공급자별 어댑터는 서버에서 비밀 저장소의 자격 증명을 사용합니다. 발송 직전에 최신 과제 상태와 월 실적, 수신 계정, 취소 여부를 다시 확인합니다. 실적이 입력되었으면 발송하지 않고 완료로 전환합니다.

상태는 `연동 대기 → 전송 대기 → 전송 중 → 발송 확인`으로 구분합니다. 공급자가 전달 확인을 지원하면 `전달 확인`을 별도로 기록합니다. 화면에서 저장하거나 파일을 생성한 시점을 발송 확인으로 사용하지 않습니다. 실제 공급자 응답 ID와 확인 시각이 있어야 발송 상태를 확정합니다.

일시적인 통신 실패·요청 제한은 공급자 지침에 맞는 지연과 횟수 제한으로 재시도합니다. 타임아웃 후 결과가 불명확하면 공급자 조회나 동일한 전송 중복 키를 사용해 중복 발송을 방지합니다. 수신 계정 오류·권한 오류는 자동 반복하지 않고 관리자 확인 대상으로 남깁니다. 예약 실행과 마감 후 재알림 주기는 운영 정책 확정 후 서버 작업으로 추가합니다.

## 결과 수신과 보안

제안 결과 주소는 `POST /api/integrations/messenger/events`입니다. 공급자가 웹훅을 지원하면 서명 검증을 적용하고, 어댑터가 내부 콜백을 보낼 때도 원문 본문에 대한 HMAC 서명과 시각·일회성 식별자를 검증합니다. 자격 증명과 서명 비밀은 서버에만 둡니다.

콜백에는 `eventId`, `requestId`, `providerMessageId`, `status`, `occurredAt`, 실패 코드가 필요합니다. `eventId`로 중복 이벤트를 제거하고, 늦게 도착한 과거 이벤트가 최신 상태를 되돌리지 못하도록 처리합니다. 공급자 오류의 민감한 원문이나 인증 토큰은 사용자 이력에 노출하지 않습니다.

## 이력과 실적 완료 처리

준비자, 수신 계정, 대상 월, 입력 기한, 요청 본문, 과제 승인 버전, 접수·시도·공급자 확인·취소·실적 입력 완료 시각과 사유를 서버에 보존합니다. 변경자는 SSO 계정으로 확정하고 클라이언트의 작성자 문자열을 인증 정보로 취급하지 않습니다.

월별 실적 저장과 관련 요청의 완료 전환을 같은 서버 흐름에서 처리합니다. 누적 진척률이 목표보다 낮아도 실적과 필수 지연 사유·Catch Up Plan이 유효하게 저장되었으면 입력 요청은 완료입니다. 과제 지연 상태와 실적 입력 요청 상태는 별도로 유지합니다.
